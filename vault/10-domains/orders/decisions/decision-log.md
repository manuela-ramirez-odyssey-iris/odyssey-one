### ORD-02 — Every Orders row click opens the Order Summary (Draft detour removed)
**Decided:** 2026-07-07
**Previous state:** `OrdersRoute` row click branched on status: `Draft` rows navigated to `/orders/create?draft=<orderNumber>` (spec §4 / plan decision 17 — reopen a session draft in the create form); all other rows opened `/orders/<orderNumber>` (Order Summary). After the S80 data unification, the shared generator seeds `'Draft'` into the unshipped-order status pool (`tools/generate.mjs` `UNSHIPPED_STATUS_POOL`, weight 20/100 ≈ 110 rows), so those generated rows also hit the create-form branch — but `getDraft()` only knows session drafts, so the form opened blank. Users experienced "random" navigation: same click, sometimes summary, sometimes an empty create flow.
**Decision / Finding:** Row click **always** opens the Order Summary page — every row, Draft included (Manuela, 2026-07-07: "Every row should open order summary when clicked"). The `?draft=` reopen path in `CreateOrderForm` is retained as a documented dev trigger; nothing navigates to it from the grid anymore. Supersedes plan decision 17's row-click detour (draft reopen as a grid behavior); a future explicit "Edit" row action can restore form-editing for drafts.
**Rationale:** Uniform, predictable navigation; the summary page renders any order (session drafts at full fidelity via `getOrderView`). Companion fix: `getOrderList`'s mock merge now has overlay rows **shadow** base rows sharing an `orderNumber` (previously `[...overlay, ...base]` with no dedupe — a draft saved over a generated row would duplicate it and collide TanStack row ids).
**Source:** User bug report + repro (S80 wrap → S81 priority 0); root-cause trace this session (generator status pool → `OrdersRoute.jsx` status branch → `getDraft` miss).
**Affects:** `apps/odyssey-one/src/routes/orders/OrdersRoute.jsx` (onRowClick), `apps/odyssey-one/src/api/services/orderService.ts` (`getOrderList` overlay shadowing), `orderService.test.ts` (+1 shadow test). Stories: LINX-10233 (View Order — the row-click target), LINX-10248 (Edit Order — where draft-reopen semantics move next).

### ORD-04 — Per-tab columns, actions, sorting, standardized pagination, Export
**Decided:** 2026-07-27
**Previous state:** `OrdersRoute`'s single grid rendered ONE shared 10-column set across all three main tabs (All/Draft/Validation Errors) regardless of which tab was active — no header sorting, row selection checkboxes present, no per-row Submit/Cancel/Resolve actions, no Export, and pagination unstandardized (no fixed default/step).
**Decision / Finding:** Each main tab now renders its own Jira/Figma-specced column set (`ordersColumns.jsx` `TAB_COLUMNS`): All = 14 data columns + Action kebab (View/Edit/Submit/Cancel/Copy/Restore per row status) with Hazmat amber badges, Order Status badges, 3-line Shipper/Destination location cells, and `--`/blank empty rules; Draft = 5 columns + kebab (Edit/Submit/Cancel, with a confirm modal on Submit/Cancel); Validation Errors = 4 columns + a direct Resolve button (enabled only while `draftOrderStatus === 'Ready'`). Header sorting is server-driven (manualSorting, one column always drives, asc↔desc) with a per-tab default (All: orderNumber desc: Draft: lastEdit desc — inference, cheap to change; Validation Errors: errorCount desc). Row-selection checkboxes are REMOVED entirely (no bulk actions surface exists yet). The toolbar's Filters button stays disabled pending the global-search/filter-panel decision; a new Export button opens a `ModalMedium` confirm (shows row count + active tab name) and streams the current tab's shape to `.xlsx` via a dynamic `xlsx` import, capped at 25,000 rows (`EXPORT_ROW_CAP`). Pagination is standardized across ALL domains (Shipments included) to page sizes 10–40 in steps of 5, default 25 (LINX-8091's audit-trail default informed the step; the standardization itself is a cross-domain Paginator change, not Orders-only).
**Rationale:** Closes the ORD-01 conformance gap (LINX-9896 grid columns/actions, LINX-11165 Export) using the actual Jira ACs + Figma per-tab mocks instead of the old lean placeholder grid; checkboxes were dropped because no bulk-action story exists yet (PO feedback + S94 user call) — adding the selection column back is cheap once one lands; standardized pagination removes a long-standing Shipments/Orders inconsistency in one pass.
**Source:** LINX-11658 (All tab AC), LINX-11663 (Draft tab + Submit confirm copy), LINX-11659 (Validation Errors tab + Resolve gating) acceptance criteria; Figma nodes 4686-5238 (All), 4686-5812 (Draft), 4686-6176 (Validation Errors); S94 user decisions (checkboxes dropped, Filters halted pending the global-search decision, pagination standardized 10–40/25 per LINX-8091, Export = current-tab Excel with a 25k cap).
**Affects:** `apps/odyssey-one/src/components/orders/ordersColumns.jsx` (new per-tab `TAB_COLUMNS`), `OrdersTable.jsx` (tab-driven columns + Action/Resolve column, checkboxes removed), `OrdersRoute.jsx` (lifted sorting state, Submit/Cancel confirm modals, Export modal wiring), `OrdersToolbar.jsx` (Export button, Filters disabled, old direction-only sort toggle removed), `OrdersExportModal.jsx` (new), `api/types/orderRowVm.ts` + `api/mappers/mapOrderListRow.ts` (per-tab VM fields; dead-code swept: `origin`/`destination`/`earlyPickup`/`commodity` VM fields + their `formatPlace`/`formatDateTime` helpers removed — superseded by `shipperLocation`/`destinationLocation`/`latestPickup`/`latestDelivery`), `api/services/orderService.ts` (`SORT_GETTERS`, submit/cancel mutations), `tools/generate.mjs` (I10 invariant: createdAt/createdBy/lastEditAt/draftOrderStatus/errorCount on every order row), `packages/ui/src/Paginator.jsx` (standardized page-size options, all domains). Stories: LINX-11658, LINX-11663, LINX-11659, LINX-11165, LINX-8091 (pagination default reference), LINX-10233/10248/10258/10259 (row actions — now wired instead of stubs).

**Previous state:** `OrdersToolbar`'s Filters button was `disabled` with the comment *"decision pending, may be superseded by global search."* `OrderListRequest.filters` already carried the LLD's All-tab fields (`orderNumbers`, `customers`, `orderStatuses`, origin/destination city-state-country, four date pairs) and `orderService.ts` already implemented every one of them in the mock — none of it was reachable from the UI. No filter existed for the Draft or Validation-Errors tabs.
**Decision / Finding:** Each tab renders its OWN filter set. This is a **ruling, not an inference**: LINX-10285's note reads "Basic filters are applicable for ~~all 3~~ **'All' tab only**" (strikethrough in the ticket). One tab-tagged registry (`src/search/orders/registry.js`) drives all three, and the phase-2 GlobalSearch integration is meant to consume it rather than restate it.
**User decisions (2026-08-20):** (1) the panel lives in the **GlobalSearch place** — opened by the navbar bar's own FilterButton, dropping beneath the bar, exactly where Shipments puts it. *(This REVERSES the first answer given earlier the same day, "toolbar now, GlobalSearch later": the toolbar-anchored panel was built, then corrected — "don't open the filters panel from whatever, respect the original panel place in global search." The Orders **search** half — query text, chips, criteria matcher, results — is still phase 2; only the panel's placement moved.)* The table toolbar's secondary Filters button **stays** — it is a TRIGGER, not a host. (Removing it was a wrong inference from "Shipments has no toolbar filter button"; the user's correction was about the panel's PLACE, not the affordance: *"don't remove our secondary button top of the table."*) So: **two triggers, one panel, one place** — the bar's FilterButton and the toolbar's Filters button both drive the same panel beneath the bar, and neither owns its open state (it is lifted to `OrdersRoute`, since the two live in different subtrees). The toolbar button carries `data-filters-trigger`, exempting it from the panel's outside-click dismissal — without it, mousedown would close the panel and the click would immediately reopen it, so the button could never close what it opened; (2) LEAN scope — fields + Apply/Clear only, no Saved/Shared/edit-profile machinery; (3) no Basic/Advanced split — the "Advanced" list is struck through in both 11663 and 11659 and was never enumerated for the All tab.
**Three AC facts Ramesh's written summary omitted, each of which changes the build:**
1. **LINX-10285 also specifies two date ranges** — Latest Pickup and Latest Delivery, From/To, MM/DD/YYYY. His summary stops at destination.
2. **The VE tab's "Order Status" is `draftOrderStatus`** (Ready/Complete/Purge, the OIF validation state per LINX-11137) — a *different vocabulary* from the All tab's 7 lifecycle labels. The ticket calls the column "Order Status", so binding it to `orderStatuses` is the easy mistake; it would filter lifecycle labels against OIF values and always return nothing. User ruling: "they might use wrong wording sometimes, is us who need to figure."
3. **Error Count needs a comparator control** — operator dropdown (Greater Than / Equals / Less Than) + integer ≥1, no decimals. No existing `attr.match`/control type covered it; built as a new `comparator` control.
**Contract extension (ours, flagged as such in the type):** `createdDateFrom/To`, `lastEditDateFrom/To`, `createdBy[]`, `lastEditedBy[]`, `draftOrderStatuses[]`, `errorCountOperator` + `errorCountValue`. Same footing as the `/order-service/v3/order/tab-counts` endpoint we already invented — the LLD's filter object covers the All tab only.
**Open contract defect, raised not patched:** the LLD models origin as three parallel arrays (`originCities`/`States`/`Countries`) ANDed together, which **cross-products on multi-select** — Miami/Florida/US + Milan/Lombardy/Italy also admits "Miami, Lombardy, Italy". The panel therefore sends BOTH the LLD arrays and an `originLocations` array of whole triples; both mock and live match on the triples and skip the mirror arrays when they are present. When Ramesh settles the shape, one representation goes away. A test pins the array-only cross-product so a future contract fix has a failing test to flip rather than a silent behaviour change.
**Whitelist trap hit again (5th instance of the class):** the panel filters worked in mock and did nothing in the running app. `api/_lib/orders.mjs` builds SQL from `ARRAY_FILTERS` / `DATE_FILTERS` **whitelist maps** — an unlisted key is silently ignored. Compounded by `.env.local` setting `VITE_API_MODE=live`, so the local app runs against the deployed Vercel function and never executes the mock service at all. Adding a field to `OrderListRequest.filters` now means adding it to the live builder too.
**Verified by driving the running app** (Playwright, mock mode — live mode proxies to the deployed function, which is not redeployed): All 1,141 → 28 on Order Status = Draft · Draft 28 → 1 on Created By = amy.cook (suggestions loaded, chip rendered) · VE 378 → 66 on draftOrderStatus = Purge · VE 378 → 376 on Error Count < 10 with the 12s and 11s gone. Panel geometry after the placement fix: 720px, centered under the bar (bar centre 728 = panel centre 728), top 56 against bar bottom 48. Both triggers verified against one panel: each opens it at the same geometry, each CLOSES what it opened, and either closes what the other opened. Bar FilterButton and toolbar button both carry the active-filter count (`Filter ①` / `Filters (1)`); Apply closes the panel; reopening re-seeds from the applied values; Escape and outside-click dismiss. The open panel overlays the tab strip, so a tab must be reached by dismissing first — same as Shipments, not a defect.
**Two layout bugs found by driving it, and only that way:** `DatePicker` carries an inline `maxWidth: 284` (a normalized component — the panel pairs the two date ranges into a two-column row rather than override it). And while the panel was still toolbar-anchored it inherited `.global-search-panel`'s `max-width: 100%` against a ~210px containing block and squeezed to 209px with its footer buttons off-screen — moot once the panel moved to the GlobalSearch slot, but the reason the toolbar anchor needed bespoke width CSS at all, which the shared placement does not.
**Control per field (user ruling, 2026-08-20 — REVISES the first pass, which made every value field a picker):**
- **Order Number → plain text input**, not a dropdown. Verbatim: *"an input field like we have in shipments which can be entered from the searchbar or not."* Order numbers are pasted off a document far more often than picked, and a picker makes the common case slower. Commas separate several values, reusing Shipments' own IN-list rule (`tokenizeChipValue` splits on commas only — a value may contain spaces).
- **Customer / Origin / Destination → ComboBox with LAZY, PAGED options.** Verbatim: *"those need to lazyload (in case they are many)."* `getOrdersAttributeValues(attr, query, skip)` returns `{ options, total }` — ComboBox's paged contract — so one 25-row page loads on focus and more arrive on scroll; the list is never fully materialised. Created By / Last Edit By were not named but are the same shape (open-ended entity lists) and follow Customer.
- **Short fixed sets (Order Status, draft status) → toggle chips.** The AC says "dropdown"; for a 3-7 value set that is intent, not a widget ruling ([[feedback_jana_does_not_decide_ui]], same principle applied to Ramesh) and it is the shipped Shipments pattern.
- **Origin and Destination sit SIDE BY SIDE** (user, 2026-08-20) — they read as a pair. Generalised the existing date-range pairing: any run of two consecutive fields of the same *pairable* control (`date-range`, `location`) becomes one two-column row. Every such run is already adjacent in the AC's own field order, so nothing is reordered.
- **The DatePicker width cap is overridden IN THIS PANEL ONLY** (user, 2026-08-20: "remove max width pickup and delivery dates for this case"). `DatePicker` carries an inline `style={{ maxWidth: 284 }}`, which left the pickers short of their grid column and misaligned against the ComboBox above. The override needs `!important` — an inline style cannot be beaten from CSS any other way — and is scoped to `.orders-filters__field > .date-picker`, so the component default is untouched and Shipments plus every form keep the 284 cap. Adding a width prop to `DatePicker` was the alternative and was rejected: a normalized-component change owes a Figma sync and an Angular twin, which is disproportionate to a panel-local layout tweak. All four paired fields now sit at 328px, flush with the full-width fields above them.
- Multi-select still lives in the panel as committed-value chips over the single-select `ComboBox`: `@odyssey/ui` has no multi-select variant and adding one is a Figma-first `/normalize` cycle. `MultiSelect` exists but takes a STATIC options array with no async loading — right for the bounded Special Services picker, wrong for anything that must page in.

**Two live-mode defects found by the user testing the real app, both fixed:**
1. **Every ComboBox loaded nothing.** `getOrdersAttributeValues` was `null` in live ("no values endpoint yet"), so the field silently degraded to plain text while still wearing a `select` chevron that opened onto nothing. The loader is now **local in BOTH modes**, following `lookupService.getLookupOptions`, whose own comment records the identical failure: *"the old live branch POSTed to /order-service/v1/<type>/lookup, got nothing, and left dropdowns empty (S95 customer-search bug)."* Serving the local pool beats serving nothing, and it needs no deploy. Restore a live branch when the lookup slice ships — this one function is the only read point.
2. **A panel Customer filter was silently discarded in live.** `getOrderList`'s live branch did `customers: customerIds`, flatly OVERWRITING the panel's own selection with the navbar scope. Mock ANDs the two (scope, then `oneOf`), so only live was wrong and the Customer filter could never work there. Now intersects, with a regression test; an empty intersection is honest (filtering to a customer outside your scope yields nothing).

**Third defect, introduced by moving the panel into the GlobalSearch slot:** every field popover inside the panel PORTALS to `document.body` (`useAnchoredPortal` for Dropdown + the DatePicker calendar; ComboBox's own `createPortal` for the typeahead list). They are visually inside the panel but DOM-outside it, so the outside-click dismissal fired and picking a Customer suggestion, an operator, or a date closed the whole panel mid-interaction. `KEEP_OPEN_SELECTOR` now exempts `[data-placement], .field-search-results` alongside the toolbar trigger. **Latent in the Shipments panel too** — same wrapper-contains check, same portaled fields — but unverified there because its ComboBoxes return no options in live, so no suggestion can be clicked to trigger it. Worth a look when the Shipments lookup path is revisited.
**Known ceiling (marked `ponytail:` in code):** the ComboBox fields have no free-text commit — `ComboBox` forwards neither `onBlur` nor `onKeyDown` once typeahead is active (`ComboBox.jsx:490,619`), so there is no prop to hang it on. Acceptable because these are pick-from-a-list fields; Order Number, the one people paste, is a plain text field precisely so it never depends on a suggestion round-trip.

### ORD-19 — Orders GlobalSearch free text: Shipments' matcher shared, not re-implemented
**Decided:** 2026-08-20
**Previous state:** The Orders bar was inert — ORD-18 shipped the FILTERS panel behind it and deferred the search half. Shipments' text semantics lived in `src/search/shipments/criteria.js`, reachable only by that domain.
**Decision / Finding:** The domain-agnostic half of that module moved to **`src/search/criteria-core.js`**; `search/shipments/criteria.js` is now a thin binding that re-exports every previous name with `FREE_TEXT_KEYS` applied, so **no Shipments call site or test changed** (verified: 260 tests across `src/search`, `gridService`, `components/global-search` green immediately after the extraction, before any Orders work). `search/orders/criteria.js` binds the same core to `ORDERS_FREE_TEXT_KEYS`. User ruling verbatim: *"the criteria is the same as in shipments."* A second implementation was the alternative and was rejected — the original extraction (S79c decision 7) exists precisely because two implementations of "what does this query mean" drift.
**What "matches the first characters" turned out to mean:** Shipments **matches on substring** (`fieldIncludes` → `String.includes`) and **ranks** prefix hits above interior ones (`scoreText`: exact 3 · starts-with 2 · contains 1). So typing the first characters of an order number puts it at the TOP, but a query appearing mid-value still matches, ranked lower. Ported verbatim rather than tightened to strict prefix, since "the same as in shipments" is the instruction — flagged to the user, and a one-line change in the core if strict prefix is the real intent.
**Multi-code union, verbatim (GS-20):** the phrase is tried WHOLE first; only if it matches nothing is it split (on whitespace or commas) and ORed. So `ERC-112330 0000000113049` returns both orders, while `Weyerhaeuser Company` stays one value instead of unioning "weyerhaeuser" with "company" and dragging in every other Company.
**Where the phrase/code-list decision is made — the one architectural call here.** It is a property of the QUERY against the WHOLE dataset, so it must be resolved ONCE, never per row and never per PAGE (per-page resolution would let page 2 disagree with page 1 about what the query meant). The client therefore sends RAW `searchText`; `getOrderList` resolves it: mock runs `textNeedles` over the full local dataset, live implements the documented **server-side twin** — run the phrase, and only if it returns zero AND tokenizes into ≥2 codes, re-run as a code list. The second round trip happens exactly in the miss case, which is the case the union exists to rescue. `searchText` never reaches the wire (`withTerms` strips it) so a second, divergent server-side resolution can't grow.
**Relevance ordering overrides the column sort while a search is active** — both in the mock and in the SQL (`GREATEST(CASE …)` mirroring `scoreText`, column sort demoted to tiebreak). Ranking a result set and then re-sorting it by created-date discards the ranking; this is the same override `gridService` applies for Shipments.
**Free-text columns are `orderNumber` + `customer` only.** `poNumber` was the obvious third — it exists on the mock row and is exactly what a customer pastes — but the live schema has **no `po_number` column** (nothing in `api/_lib/` references one), so adding it client-side alone would recreate the mock/live divergence fixed twice already this session. Keys and SQL columns are commented as mirrors of each other.
**VERIFIED IN MOCK, SILENT NO-OP IN LIVE — the deploy is now load-bearing.** Mock (Playwright): prefix `00000000` → 1,141 → 826, all matching, badge rendered; multi-code `0000000095989 ERC-` → 53 rows with the exact order first then every ERC- order; removing the badge and clearing both restore 1,141. **Live: 5,263 → 5,263, unchanged** — the deployed function ignores the unknown `searchTerms` key, so the bar renders its badge, raises no error, and filters NOTHING. This is the [[feedback_whitelist_mapper_bug_class]] shape a third time, and it now applies to a user-visible feature that *looks* like it worked. Until `api/_lib/orders.mjs` ships, Orders search must not be demoed on the live app.
**Source:** user ruling 2026-08-20 (verbatim above); Shipments S79c decision 7 / S104 GS-20 for the semantics being shared.
**Affects:** new `src/search/criteria-core.js`, rewritten `src/search/shipments/criteria.js` (binding only, behaviour identical), new `src/search/orders/criteria.js`, new `src/api/services/orderService.search.test.ts` (16), `src/api/types/orderList.ts` (+`searchText`, `searchTerms`), `src/api/services/orderService.ts` (`withTerms`, `matchesSearchTerms`, needle resolution, relevance branch), `api/_lib/orders.mjs` (+`SEARCH_COLUMNS`, `relevanceSql`, search clause, relevance ORDER BY) + `orders.test.mjs` (+5, incl. an injection guard), `OrdersGlobalSearch.jsx` (useGlobalSearch, Enter-commits, query badge), `OrdersRoute.jsx` (committed query state).

## ORD-20 — The Filters panel WRITES CHIPS: bar and panel are one criteria state (2026-08-24, S131)

**Previous state:** S130 gave one direction only — applied panel filters derive bar chips for display (`filterChips`). Typing criteria into the bar left the panel's fields empty, and the two halves ran different engines: the panel emits tab-scoped request params matched with EXACT equality (`oneOf` in mock, `= ANY()` live), the bar emits flat `searchChips` matched as case-insensitive SUBSTRINGS.
**The problem, stated precisely:** a substring criterion has no faithful param representation. `Customer: WEY` as `customers: ['WEY']` returns nothing, and the panel's ComboBox holds one exact value per field, so it cannot even display the partial. Reflecting without converting double-filters; converting silently tightens the match.
**Decision (user ruling, asked as an explicit ownership question):** for every field the BAR can also express, **the panel writes chips** — Order Number, Customer, Order Status, Draft Order Status, Created By, Last Edit By. Opening the panel seeds those fields from the committed chips; applying it replaces exactly the chips that tab speaks for and leaves bar-only chips (Equipment, Hazmat, weights) untouched. Date fields are SEEDED from a chip but emitted as params — a bar chip carries one day while the control is a From–To range, and `chipClause` reads `queryValue`, not `from`/`to`. Origin/Destination (triples) and Error Count (operator + value) have no chip vocabulary and stay params.
**Accepted cost, stated at decision time:** those six fields now match as substrings rather than exact IN-lists, so the LLD param path is exercised by locations, dates and error count only. Reversible per field if Ramesh wants exact semantics back for the ComboBox fields, whose values always come from the real value list.
**Affects:** new `src/search/orders/panelChips.js` (+ tests), `OrdersGlobalSearch.jsx` (panel seeding, `applyPanel`, criteria-based filter count), `OrdersRoute.jsx` (toolbar badge counts params + chips).

## ORD-21 — A result-row click opens the row's OWN primary action (2026-08-24, S131)

**Previous state:** rows in the search preview were not clickable at all.
**First cut, and why it was wrong:** the rule was derived from status alone — Draft → Edit, validation-error + Ready → Resolve, else View. But `allTabActionLabels` (LINX-10233) gates Edit on `orderSource === 'Manual'`, and **63 of the 102 seeded Draft orders are INTEGRATED**, whose own ⋮ menu is `['View', 'Copy']`. The rule offered an action those rows refuse. User ruling, on live order `0000000092239`: *"those row clicks are meant to be actionable/bound from the available actions, either error validation, edit or view."*
**Decision:** `primaryRowAction(row)` walks the row's REAL action list in precedence order — **Resolve** when the VE tab's own button would be enabled (validation-error status AND `draftOrderStatus === 'Ready'`), else **Edit** when the order is unfinished (draft, or erroring but not resolvable) AND its menu offers Edit, else **View**. `OrdersRoute`'s `handleRowAction` is now the single entry point shared by the ⋮ menu, the VE Resolve button and the preview, so one action name cannot mean two destinations.
**Affects:** `components/orders/ordersColumns.jsx` (+ tests), `OrdersRoute.jsx`, `search/orders/adapter.js` (rows carry the status fields as `data-*`), `OrdersGlobalSearch.jsx`.

## ORD-22 — Tab badges count the criteria, through the LIST's own predicate (2026-08-24, S131)

**Previous state:** `getOrderTabCounts(customerIds)` took no criteria at all — the badges counted the customer scope and nothing else, so a filtered grid sat under badges showing unfiltered totals. Shipments' category counts had been criteria-aware since S104.
**Decision:** the badges run the very predicate the list runs. `orderWhereClauses` was extracted from `buildOrderListQuery` (live SQL) and `applyMockFilters` from `getOrderList` (mock), and `buildTabCountsQuery` / `getOrderTabCounts` call them — a second implementation of "what does this criteria set mean" is the drift this repo has now paid for three times. The route sends the criteria MINUS the active tab's own status restriction, since each count applies its own.
**Transport, and a wrong first attempt worth keeping:** the criteria first went on a **POST** body (the natural home for an object). That 404s against an already-deployed server, and because the Tab renders `count ?? null`, the badges would have DISAPPEARED rather than gone stale. Reverted to the SAME GET path with an additive `filters=<json>` param — an old server ignores it and keeps answering, a new one narrows — verified against production before shipping. `filters` is serialized WHOLE, never field-by-field: cherry-picking chip fields into a URL is exactly what truncated the Shipments chips and made every one of those badges count 0 (same session, see below).
**Affects:** `api/_lib/orders.mjs` (`orderWhereClauses`, criteria-aware `buildTabCountsQuery`, GET `filters` parsing), `api/services/orderService.ts` (`applyMockFilters`, `mockSearchNeedles`, criteria-aware `getOrderTabCounts` with the phrase-vs-code-list two-step), `useOrderTabCounts.ts` (filters in the query key), `OrdersRoute.jsx` (`countFilters`), + tests at every layer including the route.
